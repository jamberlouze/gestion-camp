# Gestion du camp — conventions

- Code, noms de tables, colonnes et variables **en français** (sauf les tables reprises telles quelles de l'ancien Commande : `name`, `cat`, etc.).
- Un schéma Postgres par module (`core`, `embarcations`, `commande`, `horaire`, `mastertimeline`, `subventions`, `vigie`). Toute nouvelle table : RLS activée + politiques `core.peut_lire('<module>')` / `core.peut_ecrire('<module>')` (référentiel `core` : `core.est_direction()`).
- Les changements de base passent **toujours** par une migration dans `supabase/migrations/` (jamais d'édition manuelle dans le tableau de bord).
- Accès aux données côté client : `supabase.schema('<module>').from(...)` ; listes simples via `useListe` / `useEnregistrer` / `useSupprimer` (`src/lib/donnees.ts`), qui gèrent le temps réel.
- Seul le module Embarcations vise le mobile et le hors-ligne ; Cuisine et Horaire sont pensés pour ordinateur.
- Modifications hors ligne (voir `src/modules/embarcations/donnees.ts`) : chaque mutation a une clé fixe et est définie avec `clientRequetes.setMutationDefaults` (enregistrée dans `src/lib/requetes.ts` **avant** la restauration du cache), sinon une modification en attente ne peut pas reprendre après un rechargement. Mise à jour optimiste ligne par ligne ; le contexte ne garde que la ligne d'avant (jamais toute la liste). Identifiants créés côté client (`crypto.randomUUID()`).
- `gcTime` des requêtes : `Infinity` — jamais une durée > 24,8 jours (débordement de `setTimeout` : le cache restauré serait effacé aussitôt).
- Canaux temps réel : toujours un nom unique (`${nom}-${crypto.randomUUID()}`), sinon « cannot add postgres_changes callbacks after subscribe() » au remontage.
- Dans un module monté sur `<nom>/*`, les liens d'onglets sont absolus (`/embarcations/tableau`) : un lien relatif se résout depuis l'adresse courante.
- Horaire : une semaine = un document (`horaire.horaires.etat`, mêmes clés que l'ancien créateur : cellules « gid|jour|période », fusions « gid|jour|indice »), édité via `useSemaine().modifier(fn)` (copie mutée puis enregistrement automatique après 600 ms). Réglages communs dans `horaire.parametres` (clé `reglages`). Animateurs = `core.employes` actifs. Toute la logique métier est dans `logique.ts` (fonctions pures, équivalence vérifiée avec l'ancien créateur). Dossiers : `horaire.dossiers` (un niveau, nom de semaine unique par dossier). Modèles de séjour : lignes de `horaire.horaires` avec `modele = true` (jamais dans un dossier) — toute liste de « semaines » doit les exclure. Jours, périodes et nuits d'un horaire : `restructurer` (le contenu suit son jour par nom et sa période) ; modèle posé sur d'autres jours : `decalerJours` (décalage par position). `etat.nuits` absent = nuits des réglages communs.
- Mastertimeline : `taches` est le modèle, valable d'une année à l'autre (`mois` = mois civils où la tâche revient, `intervalle_ans` + `exercice_depart` pour « aux N ans » ; `mois` null = ponctuelle, avec `echeance`). Chaque passage a sa ligne dans `coches` (`periode` = 'YYYY-MM' ou 'unique' ; statut 'faite' / 'sautee' = « pas cette année » ; `note` = note de l'année, la note de `taches` est permanente). Rien n'est recopié d'une année à l'autre. Exercice d'octobre à septembre, désigné par l'année où il commence (2026 = 2026-27). Toute la logique de dates est dans `calendrier.ts` (fonctions pures). Module en ligne seulement : mutations `networkMode: 'always'` (pas de file hors ligne) ; coches lues par exercice (`useCoches`), lectures paginées par 1000. Responsables = liste propre au module (pas `core.employes`). « Aux N ans » n'est pas modifiable dans la fiche (décision de la direction : une seule tâche s'en sert) ; la colonne `jour` n'est plus utilisée. `projets.entreprise_ids` = entreprises où le projet est offert dans la fiche (vide = toutes), voir `offertPour`.
- Cuisine (ex-Commande ; dossier `modules/commande`, schéma `commande`, module `commande`, adresse `/cuisine`) : un menu = une ligne de `commande.menus` (nom, jours, debut) ; ses groupes, grille, sorties et ajouts manuels sont dans leurs tables avec `menu_id` (lus par `useTableMenu(table, menuId)`, clé `[commande, table, menuId]` ; toute écriture porte `menu_id`). Recettes, consommables et banque restent communs (`useTable`). Dossiers : `commande.dossiers` ; modèles : `menus.modele = true` (ni dossier ni date). Copier un menu (dupliquer, modèle → menu) : fonction SQL `commande.copier_menu` (les groupes gardent leur id, clé `(menu_id, id)`) ; créer un menu vide : `commande.creer_menu` (menu + premier groupe en une transaction). Module en ligne seulement : mutations `networkMode: 'always'` ; une erreur affichée sur place est retirée du bandeau (`useOublierErreur`). Végé par groupe (`groupes_repas.vege`, comprises dans `portions`) : recette avec option végé → régulier = portions − végé ; en sortie, `sorties.groupes[].vege` = végé partis (au moins ceux qui ne tiennent plus au camp), servis par l'option végé de la glacière (`vegeSorties`). Diètes standard par groupe : `vege` (végétarienne, comptée dans la commande), `sans_porc`, `sans_lactose`, `sans_gluten` (information seulement) ; une diète par participant, régulière = portions − les autres. Participants avec allergies : `commande.participants` (clé étrangère `(menu_id, groupe_id)`, copiés par `copier_menu`) ; onglet « Groupes et diètes » (`Groupes.tsx`, une page imprimée par groupe), rappel par repas sur la feuille de cuisine. Impression : la feuille de cuisine a sa propre version papier compacte (`FeuilleImprimee`, un jour par page) ; l'horaire remplit une page paysage. Calcul de la commande dans `calcul.ts` (fonction pure ; avec végé = 0, identique à l'ancien calculateur, sauf qu'un même # produit en deux unités donne deux lignes : `cleLigne`) ; feuille de cuisine dans `cuisine.ts` (même calcul repas par repas : feuille + consommables = commande). Horaire du personnel : `personnel` (liste propre au module), `fonctions` (couleur), `quarts` (une case = texte libre par personne et par jour, heures lues par `quarts.ts`), réglages dans `parametres` (clé `horaire_cuisine`) ; copier ou vider une semaine : `commande.remplacer_quarts` (une transaction).
- Subventions (« Vigie de subventions », schéma et module `subventions`, adresse `/subventions`) : **administrateurs et direction seulement** — RLS sur `core.est_direction()` (pas `peut_lire`), `directionSeulement: true` dans `src/shell/modules.ts` (jamais offert aux coordonnateurs dans Utilisateurs, absent de la contrainte de `core.acces_modules`). Tables et colonnes en anglais, reprises telles quelles de la feuille de route (`grants`, `grant_companies`, `grant_feedback`…) ; fonctions SQL en français. Année fiscale du 1er octobre au 30 septembre nommée d'après l'année où elle **se termine** (`subventions.fiscal_year`, `anneeFiscale` dans `outils.ts` ; 2026 = « 2025-26 ») — l'inverse de Mastertimeline ; une subvention est rattachée à l'année de `granted_at`, sinon `received_at`, `deadline_date`, découverte (`dateRattachement`). Statuts : `nouveau` (pas regardée), `a_valider` (en attente d'une info), `rejete` (feedback obligatoire), `en_cours`, `obtenu`, `refuse` (refusée par l'organisme, ajout à la feuille de route), `expire`. Valider / rejeter passe par `subventions.decider` (statut + feedback en une transaction) ; un rejet n'est jamais reproposé. Dédoublonnage dans `subventions.inserer_resultats` : même adresse normalisée ou même `program_key` pour la même entreprise ; un programme obtenu/refusé/expiré une année précédente revient comme nouvelle édition (`previous_grant_id`). Notes et heures : modifiables seulement par leur auteur. Recherche : `worker/subventions/` (pipeline, prompts, appels Claude par le SDK officiel, courriel par l'API Gmail), cron du lundi 8 h–11 h UTC partagé avec le waker (une entreprise par passage, journal `grant_search_runs`), routes `/api/subventions/{etat,recherche,courriel}` protégées par le jeton de session (`subventions.peut_utiliser`). Secrets Cloudflare seulement (README, section 8). Tests : `npm run test:worker` (réseau simulé). Erreurs affichées dans une fenêtre : racine de mutation `subventions-local` (le bandeau du module l'ignore).
- Styles : Tailwind v4, classes partagées dans `src/lib/ui.ts`, couleurs `foret-*` / `pierre-*` (`src/index.css`). Fond de page blanc. Cadre unique (`src/shell/Layout.tsx`) : pleine largeur et mêmes marges pour tous les modules — pas de largeur propre à un module (le menu et les marges ne doivent pas bouger d'un module à l'autre). Menus déroulants : flèche maison globale (`src/index.css`, règle hors couche qui impose l'espace à droite) ; `sans-fleche` pour un menu-bouton, `fleche-serree` pour un tout petit menu. Icônes : `src/lib/icones.tsx`. Saisie d'un nom : `SaisieNom` / `Bulle` (`src/lib/SaisieNom.tsx`) plutôt que `prompt()` ; confirmation : `await confirmer({ titre, message?, libelleOk?, danger? })` (`src/lib/Confirmation.tsx`, hôte `<Confirmations />` monté dans `main.tsx`) plutôt que `confirm()`.
- Node est dans `/usr/local/bin` (installateur officiel, pas Homebrew — macOS 14 non supporté par Homebrew).
- Vigie des camps (dossier `modules/vigie`, schéma `vigie`, adresse `/vigie`, direction seulement) : rien de ce que Claude trouve n'est appliqué à un camp suivi sans validation — tout passe par `vigie.changements` (prix, nouveau programme, nouvelle activité), appliqué par `vigie.valider_changement` (une transaction). Exception : la passe 2 (`documentation`, lancée par le déclencheur quand un camp proposé devient inclus) remplit la fiche directement. Appels à Claude : une ligne par appel dans `vigie.requetes_ia` (file), envoyées en lot (Message Batches) par la fonction Edge `supabase/functions/vigie` (réveillée par pg_cron `vigie-tic` toutes les 10 min via `vigie.tic()`, seulement s'il y a du travail ; `vigie.planifier()` chaque jour lance la mensuelle le 1er et la découverte à `prochaine_decouverte`). `pause_turn` : la conversation est gardée dans `donnees.messages` et renvoyée au lot suivant. Activités = liste candidate commune (`activites`, pas de fiche par camp) liée par `camps_activites` ; un camp exclu reste en base pour ne jamais être reproposé. Prix par nuit = colonne générée. Maquette 3D : scène JSON de formes simples (boite, cylindre, sphere, cone ; mètres, y vers le haut), rendue sans bibliothèque en Canvas 2D (`Maquette3D.tsx`). Pas de mémoire auto-apprenante : ajustements à la main dans Réglages (`consignes`). Import du Sheets : `scripts/migration/vigie.py`.
