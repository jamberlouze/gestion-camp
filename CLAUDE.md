# Gestion du camp — conventions

- Code, noms de tables, colonnes et variables **en français** (sauf les tables reprises telles quelles de l'ancien Commande : `name`, `cat`, etc.).
- Un schéma Postgres par module (`core`, `embarcations`, `commande`, `horaire`, `mastertimeline`, `subventions`, `vigie`, `calendrier`, `temps`, `vehicules`, `travaux`, `achats`, `rooming`, `caisse`, `ameliorations`, `reunions`, `crm`, `reservations`, `inventaire`, `rh`, `batiments` ; Coût par assiette est dans `commande`). Toute nouvelle table : RLS activée + politiques `core.peut_lire('<module>')` / `core.peut_ecrire('<module>')` (référentiel `core` : `core.est_direction()`).
- **Employés** (`core.employes`, Référentiel › Employés, premier onglet du référentiel) : `surnom` = « Nom de camp » à l'écran, `prenom` + `nom_famille` (demande de Maxime) ; `nom_complet` (« Nom, Prénom ») est posé par le déclencheur `core.poser_nom_complet`, ne jamais l'écrire. `matricule_employeur_d` = matricule Employeur D (paie ; un par employé, le même pour toutes ses compagnies, choix de Maxime ; 9 chiffres au plus, unique, nettoyé par `core.verifier_matricule_employeur_d`) : le module RH le lit par `rh.personnes.employe_id`, jamais de deuxième colonne de matricule. Ordre des onglets du référentiel : Employés, Compagnies, Groupes, Semaines.
- **Compagnies** = `core.entreprises` (Référentiel › Compagnies, demande de Maxime : une seule liste dans l'app ; nom, abréviation, description, couleur, ordre, `numero_employeur_d` (numéro de compagnie Employeur D, 8 lettres ou chiffres, unique, `core.verifier_numero_employeur_d`), active ; lue par toute personne active, modifiée par la direction). Ex-`mastertimeline.entreprises` déplacée telle quelle (mêmes id). S'en servent : Mastertimeline (tâches, `projets.entreprise_ids`), Achats, Véhicules (`vehicules.proprietaire_id`, ex-`vehicules.proprietaires`), Vigie de subventions (`grant_companies.entreprise_id`, une recherche par compagnie ; `grant_companies.name` = copie du nom tenue par la base : déclencheurs `subventions.nom_compagnie` et `core.renommer_compagnie`), Feuilles de temps (`core.employes.entreprise_ids`, heures par compagnie). Nouvelle liste de compagnies dans un module : non, utiliser celle-ci. Couleurs (choix de Maxime) : GBPA+ vert, Opikawa orange, Aquabounga jaune, Rouge & Diable rouge, Trembloc brun, BPA inc. gris ; toute étiquette d'une compagnie = `PuceCompagnie` (`src/lib/PuceCompagnie.tsx`, teinte de sa couleur, `court` = abréviation), pastilles « choix » du référentiel teintées par `Option.couleur`.
- Qui voit quel module : **grille d'accès par rôle** `core.acces_roles` (rôle `direction`/`coordo`/`terrain`/`developpeur` × module → `lecture`/`ecriture` ; absent = aucun), réglée par les admins dans la page Utilisateurs. L'admin a tout, toujours. Un nouveau compte arrive avec le rôle `terrain` (défaut de `core.profils.role`) : l'admin le change pour la direction ou un coordonnateur. Toute autre personne a en plus ses ajouts personnels (`core.acces_modules`, bouton « Ajouter un module » sur sa ligne) ; le niveau le plus élevé l'emporte. Seul endroit qui décide : `core.niveau_module_de(user, module)` (derrière `peut_lire`/`peut_ecrire`, la fonction Edge vigie, les destinataires de Subventions) ; même règle côté app dans `src/shell/acces.ts` (`niveauModule`, affichage seulement). Subventions et Vigie peuvent aussi aller aux coordonnateurs ; `sansLecture` : pas de mode lecture seule dans l'app (Subventions : écriture ou rien) ; `accesFixe` : hors grille (Feuilles de temps) ; `cacheSaufAdmins` : module mis en pause, caché à tous sauf les admins (menu, accueil, adresse : `peutOuvrir`), droits et données inchangés (`peutLire`). Nouveau module : l'ajouter aux contraintes `module in (…)` de `acces_roles` et `acces_modules`, et à la grille de la direction si elle doit le voir.
- **DEV et PROD séparés** (l'équipe utilise l'app). DEV = Supabase **local** dans Docker (`npm run db:start` / `db:reset` / `db:stop` ; Docker Desktop doit rouler, binaire dans `/Applications/Docker.app/Contents/Resources/bin`) ; `.env.local` vise la base locale (`http://127.0.0.1:54321`), **jamais la PROD**. Données de test : `supabase/seed.sql` (comptes `*@camp.test`, codes de connexion dans Mailpit, http://localhost:54324 ; `db:start` coupe le SMTP Gmail de `config.toml` par variable d'environnement). PROD = projet hébergé `nurjzafcogzgekquzuwh` : `npm run prod:db:push` (migrations) et `prod:db:config`, puis push sur `main` (Cloudflare publie). Une migration n'est appliquée en PROD qu'une fois testée en local et validée par Maxime.
- **Deux branches seulement** (décision de Maxime, il est seul à développer) : `dev` = la version DEV, où l'on travaille toujours (commit puis `git push` sur `dev` : simple sauvegarde, Cloudflare ne publie que `main`) ; `main` = la PROD, jamais modifiée directement. Un module à la fois : le finir et le mettre en ligne avant d'en commencer un autre. Mise en ligne uniquement par la commande `/mise-en-ligne` (fusion de `dev` dans `main`, migrations PROD, push), après un « oui » explicite de Maxime. Pas de branche de chantier ni de worktree. Nouvelle migration : nommée à l'heure **UTC** (`npx supabase migration new <nom>` ou `date -u +%Y%m%d%H%M%S`), jamais un numéro inventé.
- Les changements de base passent **toujours** par une migration dans `supabase/migrations/` (jamais d'édition manuelle dans le tableau de bord).
- Accès aux données côté client : `supabase.schema('<module>').from(...)` ; listes simples via `useListe` / `useEnregistrer` / `useSupprimer` (`src/lib/donnees.ts`), qui gèrent le temps réel.
- Seuls Embarcations, Travaux, Inventaire et Bâtiments visent le mobile et le hors-ligne ; Cuisine et Horaire sont pensés pour ordinateur.
- Modifications hors ligne (voir `src/modules/embarcations/donnees.ts`) : chaque mutation a une clé fixe et est définie avec `clientRequetes.setMutationDefaults` (enregistrée dans `src/lib/requetes.ts` **avant** la restauration du cache), sinon une modification en attente ne peut pas reprendre après un rechargement. Mise à jour optimiste ligne par ligne ; le contexte ne garde que la ligne d'avant (jamais toute la liste). Identifiants créés côté client (`crypto.randomUUID()`).
- `gcTime` des requêtes : `Infinity` — jamais une durée > 24,8 jours (débordement de `setTimeout` : le cache restauré serait effacé aussitôt).
- Canaux temps réel : toujours un nom unique (`${nom}-${crypto.randomUUID()}`), sinon « cannot add postgres_changes callbacks after subscribe() » au remontage.
- Dans un module monté sur `<nom>/*`, les liens d'onglets sont absolus (`/embarcations/tableau`) : un lien relatif se résout depuis l'adresse courante.
- Horaire (« Animation » dans l'app) : une semaine = un document (`horaire.horaires.etat`, mêmes clés que l'ancien créateur : cellules « gid|jour|période », fusions « gid|jour|indice »), édité via `useSemaine().modifier(fn)` (copie mutée puis enregistrement automatique après 600 ms). Réglages communs dans `horaire.parametres` (clé `reglages`). Animateurs = `core.employes` actifs. Toute la logique métier est dans `logique.ts` (fonctions pures, équivalence vérifiée avec l'ancien créateur). Dossiers : `horaire.dossiers` (un niveau, nom de semaine unique par dossier). Modèles de séjour : lignes de `horaire.horaires` avec `modele = true` (jamais dans un dossier) — toute liste de « semaines » doit les exclure. Jours, périodes et nuits d'un horaire : `restructurer` (le contenu suit son jour par nom et sa période) ; modèle posé sur d'autres jours : `decalerJours` (décalage par position). `etat.nuits` absent = nuits des réglages communs.
- Mastertimeline : `taches` est le modèle, valable d'une année à l'autre (`mois` = mois civils où la tâche revient, jamais null : les tâches et projets ponctuels sont dans Travaux ; `intervalle_ans` + `exercice_depart` pour « aux N ans »). Chaque passage a sa ligne dans `coches` (`periode` = 'YYYY-MM' ; statut 'faite' / 'sautee' = « pas cette année » ; `note` = note de l'année, la note de `taches` est permanente). Rien n'est recopié d'une année à l'autre. Exercice d'octobre à septembre, désigné par l'année où il commence (2026 = 2026-27). Toute la logique de dates est dans `calendrier.ts` (fonctions pures). Module en ligne seulement : mutations `networkMode: 'always'` (pas de file hors ligne) ; coches lues par exercice (`useCoches`), lectures paginées par 1000. Responsables = liste propre au module (pas `core.employes`). « Aux N ans » n'est pas modifiable dans la fiche (décision de la direction : une seule tâche s'en sert) ; la colonne `jour` ne sert pas. Entreprises = `core.entreprises` (référentiel, pas de liste propre au module ; pas d'onglet Entreprises dans Réglages, seulement un lien vers Référentiel › Compagnies, l'ancienne adresse y mène). Réglages (Responsables, Fournisseurs, Projets, Étiquettes) = `TableauReferentiel`, comme le Référentiel (demande de Maxime : même visuel). Toute la ligne d'une tâche ouvre sa fiche, dans toutes les vues (même règle que Travaux). `projets.entreprise_ids` = entreprises où le projet est offert dans la fiche (vide = toutes), voir `offertPour`. Étiquettes (tags, demande de Maxime : Corvée, ex-case à cocher, et Woofing) : liste du module `etiquettes` (Réglages), posées par `taches.etiquette_ids` (plusieurs par tâche) ; supprimer une étiquette la retire des tâches de Mastertimeline et de Travaux (déclencheur `retirer_etiquette`) ; filtre en puces (`ChoixEtiquettes`, `src/lib/Etiquettes.tsx` : plusieurs allumées = l'une ou l'autre) dans toutes les vues ; dans chaque ligne des deux modules (vue Année comprise), pastille de sa couleur + nom (`PucesEtiquettes`), couleur réglée dans Réglages › Étiquettes. Photos et PDF (demande de Maxime) : `fichiers`, joints à la **tâche** (le modèle, valables toutes les années, pas au passage), seau **privé** `mastertimeline-fichiers` lu par adresses signées (`useAdresseFichier`, requêtes `['mastertimeline-adresses', …]` jamais gardées sur l'appareil), même affichage que Travaux (`src/lib/PiecesJointes.tsx`) ; envoyés tout de suite depuis la fiche d'une tâche existante. **Un onglet par étiquette** (`VueEtiquette.tsx`, `/mastertimeline/etiquette/:id`, demande de Maxime, direction seulement : onglet de Mastertimeline) : tâches de Mastertimeline **et de Travaux** qui la portent, mois choisi + retards (Travaux : ouvertes = mois en cours, échéance passée = en retard ; autre mois = dues ou faites ce mois-là ; annualisées exclues) ; choix **Mois | Année** (demande de Maxime, gardé sur l'appareil) : Année = l'exercice complet, une carte par mois (Travaux : ouvertes au mois de leur échéance, sans échéance ou échues avant l'exercice au mois en cours ; faites au mois où elles l'ont été).
- Cuisine (ex-Commande ; dossier `modules/commande`, schéma `commande`, module `commande`, adresse `/cuisine`) : un menu = une ligne de `commande.menus` (nom, jours, debut) ; ses groupes, grille, sorties et ajouts manuels sont dans leurs tables avec `menu_id` (lus par `useTableMenu(table, menuId)`, clé `[commande, table, menuId]` ; toute écriture porte `menu_id`). Recettes, consommables et banque restent communs (`useTable`). Dossiers : `commande.dossiers` ; modèles : `menus.modele = true` (ni dossier ni date). Copier un menu (dupliquer, modèle → menu) : fonction SQL `commande.copier_menu` (les groupes gardent leur id, clé `(menu_id, id)`) ; créer un menu vide : `commande.creer_menu` (menu + premier groupe en une transaction). Module en ligne seulement : mutations `networkMode: 'always'` ; une erreur affichée sur place est retirée du bandeau (`useOublierErreur`). Végé par groupe (`groupes_repas.vege`, comprises dans `portions`) : recette avec option végé → régulier = portions − végé ; en sortie, `sorties.groupes[].vege` = végé partis (au moins ceux qui ne tiennent plus au camp), servis par l'option végé de la glacière (`vegeSorties`). Diètes standard par groupe : `vege` (végétarienne, comptée dans la commande), `sans_porc`, `sans_lactose`, `sans_gluten` (information seulement) ; une diète par participant, régulière = portions − les autres. Participants avec allergies : `commande.participants` (clé étrangère `(menu_id, groupe_id)`, copiés par `copier_menu`) ; onglet « Groupes et diètes » (`Groupes.tsx`, une page imprimée par groupe), rappel par repas sur la feuille de cuisine. Impression : la feuille de cuisine a sa propre version papier compacte (`FeuilleImprimee`, un jour par page) ; l'horaire remplit une page paysage. Calcul de la commande dans `calcul.ts` (fonction pure ; avec végé = 0, identique à l'ancien calculateur, sauf qu'un même # produit en deux unités donne deux lignes : `cleLigne`) ; feuille de cuisine dans `cuisine.ts` (même calcul repas par repas : feuille + consommables = commande). Horaire du personnel : `personnel` (liste propre au module), `fonctions` (couleur), `quarts` (une case = texte libre par personne et par jour, heures lues par `quarts.ts`), réglages dans `parametres` (clé `horaire_cuisine`) ; copier ou vider une semaine : `commande.remplacer_quarts` (une transaction).
- Cuisine › **Coût par assiette** (dossier `modules/commande/couts`, tables `commande.couts_*`, adresse `/cuisine/couts`, demande de Maxime ; remplace le Google Sheets « Suivi coût par assiette 2026 ») : **accès propre** dans la grille, module `cuisine_couts` (RLS `peut_lire/peut_ecrire('cuisine_couts')`) — c'est un espace de Cuisine, pas une entrée du menu : `parent: 'commande'` dans `modules.ts` (`estEntree` l'écarte du menu, de l'accueil et de `GRILLE_AVANT`) ; aucune ligne dans la grille (montre les salaires) : admins + Frédérique (responsable de la cuisine) en ajout personnel. Coût par assiette = (nourriture + salaires) ÷ assiettes. **Tout est rattaché à des jours** puis additionné selon **deux vues** (choix de Maxime) : **Année** = 12 mois civils d'octobre à septembre (calculés, rien à saisir) et **Camp d'été** = les semaines de `couts_semaines` (par année, définies dans l'onglet Semaines, sans chevauchement ; 8 proposées à partir du dernier dimanche de juin), avec l'écart de chaque semaine à la moyenne de l'été. Chaque vue a un graphique (`Graphique.tsx`, demande de Maxime) : trois petits graphiques en ligne sur le même axe (coût par assiette, coût, assiettes ; jamais deux échelles sur un même graphique), curseur et infobulle communs. Années (`couts_annees`) désignées par l'année où elles commencent (comme Mastertimeline). **Factures** (`couts_factures`, crédit = négatif) : comptées au `jour_impute` s'il est posé (date d'imputation à la main : nourriture livrée pour plus tard), sinon au jour de livraison. **Salaires** (`couts_salaires`) : un montant par période de paie (14 jours du dimanche, mêmes périodes que les Feuilles de temps) et par poste (`couts_postes`), partagé également entre les 14 jours (choix de Maxime : pas de pondération par l'horaire). **Assiettes** : menus datés de Cuisine calculés jour par jour (à chaque repas planifié — plat, salade ou dessert —, les portions des groupes présents ; un groupe en sortie compte), total corrigible par menu (`couts_menus`, réparti comme le calcul), plus groupes ajoutés (`couts_groupes`, personnes × repas répartis également du `debut` à la `fin` ; sans dates = à classer, pas compté ; l'année suit `debut`) ; `couts_annees.menus = false` : les menus ne comptent pas (2025-2026, importée du Sheets). Calculs dans `calcul.ts` (fonctions pures : `journalier` puis `tableau`). Pas de temps réel ni de cache sur l'appareil (`['cuisine-couts', …]` exclues de la persistance). Module en ligne seulement ; erreurs dans le bandeau de l'espace (racine `cuisine-couts`), fenêtres sur place (`cuisine-couts-local`). Import 2025-2026 dans la migration (10 semaines du Sheets ; factures placées par ✅ ailleurs que leur livraison = imputées au premier jour de la période du Sheets ; groupes datés sur leur période ; nourriture 142 645,61 $, assiettes 31 323, salaires 76 882,19 $ ; les totaux du Sheets ne comptaient que mai à septembre).
- Subventions (« Vigie de subventions », schéma et module `subventions`, adresse `/subventions`) : accès par la grille par rôle ou en ajout personnel (écriture ou rien ; admins seulement au départ). Entreprises de recherche (`grant_companies`) = profil de recherche d'une compagnie du référentiel (`entreprise_id` unique ; nom lu dans `core.entreprises`, ajout par un menu des compagnies sans recherche ; « Base de Plein Air Mont-Tremblant », l'OBNL = GBPA+). `subventions.a_acces()` = `core.peut_ecrire('subventions')` (RLS, déclenchement manuel du Worker par `peut_utiliser`). **Aucun courriel, jusqu'à nouvel ordre** (décision de Maxime) : ce module n'en envoie aucun, **ne pas en rajouter** (rappel éteint par `COURRIELS = false` dans `pipeline.js`, route `courriel` = 410 ; `courriel.js`, `destinataires()` et `grant_digests` gardés). Tables et colonnes en anglais, reprises telles quelles de la feuille de route (`grants`, `grant_companies`, `grant_feedback`…) ; fonctions SQL en français. Année fiscale du 1er octobre au 30 septembre nommée d'après l'année où elle **se termine** (`subventions.fiscal_year`, `anneeFiscale` dans `outils.ts` ; 2026 = « 2025-26 ») — l'inverse de Mastertimeline ; chaque subvention a son année `grants.fiscal_year`, **proposée** par le déclencheur `subventions.poser_annee_fiscale` (période financée `funded_start`, sinon date limite, sinon octroi, sinon année de la découverte ; même règle dans `anneeFiscaleProposee`) et **modifiable sur la fiche** (`fiscal_year_manual`) ; Suivi et Attribution salariale la lisent ; `discovered_fy` ne sert qu'au dédoublonnage. Statuts : `nouveau` (pas regardée), `a_valider` (en attente d'une info), `rejete` (feedback obligatoire), `en_cours`, `obtenu`, `refuse` (refusée par l'organisme, ajout à la feuille de route), `expire`. Valider / rejeter passe par `subventions.decider` (statut + feedback en une transaction) ; un rejet n'est jamais reproposé. Dédoublonnage dans `subventions.inserer_resultats` : même adresse normalisée ou même `program_key` pour la même entreprise ; un programme obtenu/refusé/expiré une année précédente revient comme nouvelle édition (`previous_grant_id`). Notes et heures : modifiables seulement par leur auteur. Recherche : `worker/subventions/` (pipeline, prompts, appels Claude par le SDK officiel) ; le prompt (`invitationRecherche`) tire le contexte du groupe de `grant_companies` (rien à tenir à jour), met la priorité salariale seulement si `hires_staff`, et ajoute le réglage facultatif `consignes_groupe`. **4 fois par année** (décision de Maxime : du 1er au 7 octobre, janvier, avril et juillet, heure pile de 8 h à 11 h UTC, `estTourTrimestriel` ; le cron aux 15 min appelle `passageSubventions`, qui fait aussi l'agenda et `expirer_echues` chaque jour à 8 h UTC), **en deux temps**, un travail par passage choisi par `subventions.prochaine_tache_trimestre` : (a) recherche large par entreprise (`grant_search_runs.kind = 'large'`) ; (b) mise à jour ciblée (`ciblee`) des retenues de l'entreprise (`retenues_a_verifier` : en cours, ou obtenues de l'année ou la précédente sans édition suivante ; 10 par appel, `invitationMiseAJour`) appliquée par `subventions.appliquer_mise_a_jour` : champ vide rempli directement (trace `appliquee`), champ rempli qui changerait = proposition `grant_proposals` à accepter ou refuser sur la fiche (`decider_proposition` ; jamais écrasé sans accord ; une valeur refusée n'est pas reproposée) ; une obtenue ne change jamais, sa nouvelle édition devient une subvention `nouveau` liée par `previous_grant_id`. « Lancer maintenant » (onglet Recherches) fait l'un ou l'autre pour une entreprise ; routes `/api/subventions/{etat,recherche,agenda}` protégées par le jeton de session (`subventions.peut_utiliser`). **Agenda Google « Subventions »** (dédié, jamais l'agenda d'inscription) : retenue ou obtenue → ouverture et date limite, obtenue → aussi les étapes de reddition pas faites (journée entière, rien avant `agenda.depuis`) ; règles pures dans `agenda.ts` (app et Worker), écrit par `worker/subventions/agenda.js` avec le client minimal `worker/commun/agendaGoogle.js` (jamais celui des Réservations), aux 15 min et 1,5 s après un changement sur la fiche ; `grant_calendar_events` (clé `ouverture:`/`fermeture:<subvention>`, `reddition:<étape>`, sans clé étrangère : ce qui n'est plus voulu est retiré) ; réglage `agenda` (`actif`, `calendrier`, `depuis`) ; base locale = simulé (`essai-subventions`) ; jeton `SUBVENTIONS_AGENDA_REFRESH_TOKEN`. **Attribution salariale** (onglet, `AttributionSalariale.tsx`) : `grant_salary_lines`, un employé (`core.employes`, `on delete restrict`, ou `free_name` pour un poste à pourvoir) sur une subvention ; salaire = `salary_amount`, sinon taux × heures ; employeur vide = salaire − subvention ; % couvert = subvention ÷ (subvention + employeur) (`calculLigne`, `totauxSalaires`) ; un tableau par année fiscale, filtre par entreprise ; salaires : RLS du module, ni temps réel ni cache sur l'appareil (`['subventions-salaires', …]`). Heures investies : en suspens (décision avec Marco), ne pas y toucher. Secrets Cloudflare seulement (README, section 8). Tests : `npm run test:worker` (réseau simulé). Erreurs affichées dans une fenêtre : racine de mutation `subventions-local` (le bandeau du module l'ignore).
- Boutons « Modifier » / « Supprimer » : toujours `BoutonModifier` / `BoutonSupprimer` (`src/lib/BoutonsAction.tsx` : même forme, crayon ; poubelle et texte rouge), avec un texte précis au besoin (« Supprimer la série »). Exception : les poubelles icône seule dans les listes compactes.
- Styles : Tailwind v4, classes partagées dans `src/lib/ui.ts`, couleurs `foret-*` / `pierre-*` (`src/index.css`). Fond de page blanc. Cadre unique (`src/shell/Layout.tsx`) : pleine largeur et mêmes marges pour tous les modules — pas de largeur propre à un module (le menu et les marges ne doivent pas bouger d'un module à l'autre). Navigation (`Layout.tsx` + `Menu.tsx`, version A des maquettes en compact, décision de Maxime) : **menu par familles** — Opérations, Bâtiment et matériel, Gestion, Équipe ; la famille = champ `famille` de chaque module dans `modules.ts` (ordre dans la famille = ordre de `MODULES`, aussi celui de la grille d'accès ; titres et noms courts : `FAMILLES`) ; une **liste icône + nom** (lignes de 28 px sur ordinateur, 36 px dans le tiroir du téléphone) sous un titre de famille discret avec sa petite icône au trait (la même que dans le menu réduit) ; **chaque famille se replie** d'un clic sur son titre (gardé sur l'appareil, `menu-familles-repliees` ; une famille repliée garde le module de la page ouverte) ; Améliorations, Référentiel et Utilisateurs 🔑 (RH garde 👥) en **rangée d'icônes en bas** (famille `bas`), nom en info-bulle au survol et au focus clavier, `aria-label` sur chaque lien ; tout le menu d'un admin tient sans défiler à 800 px de haut, familles ouvertes. Module sans accès = absent, famille vide = cachée, **moins de 7 entrées en tout = liste à plat avec les noms** (ex. Terrain) ; module `cacheSaufAdmins` grisé et marqué « admins ». **Pas d'entrée « Accueil »** : le logo y ramène (aussi dans le menu réduit).
