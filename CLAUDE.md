# Gestion du camp — conventions

- Code, noms de tables, colonnes et variables **en français** (sauf les tables reprises telles quelles de l'ancien Commande : `name`, `cat`, etc.).
- Un schéma Postgres par module (`core`, `embarcations`, `commande`, `horaire`, `mastertimeline`, `subventions`, `vigie`, `calendrier`, `temps`, `vehicules`). Toute nouvelle table : RLS activée + politiques `core.peut_lire('<module>')` / `core.peut_ecrire('<module>')` (référentiel `core` : `core.est_direction()`).
- Qui voit quel module : **grille d'accès par rôle** `core.acces_roles` (rôle `direction`/`coordo` × module → `lecture`/`ecriture` ; absent = aucun), réglée par les admins dans la page Utilisateurs (décision du 2026-10-05). L'admin a tout, toujours. Toute autre personne a en plus ses ajouts personnels (`core.acces_modules`, bouton « Ajouter un module » sur sa ligne) ; le niveau le plus élevé l'emporte. Seul endroit qui décide : `core.niveau_module_de(user, module)` (derrière `peut_lire`/`peut_ecrire`, la fonction Edge vigie, les destinataires de Subventions) ; même règle côté app dans `src/shell/acces.ts` (`niveauModule`, affichage seulement). Subventions et Vigie peuvent aussi aller aux coordonnateurs (décision du 2026-10-05) ; `sansLecture` : pas de mode lecture seule dans l'app (Subventions : écriture ou rien) ; `accesFixe` : hors grille (Feuilles de temps). Nouveau module : l'ajouter aux contraintes `module in (…)` de `acces_roles` et `acces_modules`, et à la grille de la direction si elle doit le voir.
- **DEV et PROD séparés** (depuis le 2026-10-06 : l'équipe utilise l'app). DEV = Supabase **local** dans Docker (`npm run db:start` / `db:reset` / `db:stop` ; Docker Desktop doit rouler, binaire dans `/Applications/Docker.app/Contents/Resources/bin`) ; `.env.local` vise la base locale (`http://127.0.0.1:54321`), **jamais la PROD**. Données de test : `supabase/seed.sql` (comptes `*@camp.test`, codes de connexion dans Mailpit, http://localhost:54324 ; `db:start` coupe le SMTP Gmail de `config.toml` par variable d'environnement). PROD = projet hébergé `nurjzafcogzgekquzuwh` : `npm run prod:db:push` (migrations) et `prod:db:config`, puis push sur `main` (Cloudflare publie). Une migration n'est appliquée en PROD qu'une fois testée en local et validée par Maxime.
- Les changements de base passent **toujours** par une migration dans `supabase/migrations/` (jamais d'édition manuelle dans le tableau de bord).
- Accès aux données côté client : `supabase.schema('<module>').from(...)` ; listes simples via `useListe` / `useEnregistrer` / `useSupprimer` (`src/lib/donnees.ts`), qui gèrent le temps réel.
- Seul le module Embarcations vise le mobile et le hors-ligne ; Cuisine et Horaire sont pensés pour ordinateur.
- Modifications hors ligne (voir `src/modules/embarcations/donnees.ts`) : chaque mutation a une clé fixe et est définie avec `clientRequetes.setMutationDefaults` (enregistrée dans `src/lib/requetes.ts` **avant** la restauration du cache), sinon une modification en attente ne peut pas reprendre après un rechargement. Mise à jour optimiste ligne par ligne ; le contexte ne garde que la ligne d'avant (jamais toute la liste). Identifiants créés côté client (`crypto.randomUUID()`).
- `gcTime` des requêtes : `Infinity` — jamais une durée > 24,8 jours (débordement de `setTimeout` : le cache restauré serait effacé aussitôt).
- Canaux temps réel : toujours un nom unique (`${nom}-${crypto.randomUUID()}`), sinon « cannot add postgres_changes callbacks after subscribe() » au remontage.
- Dans un module monté sur `<nom>/*`, les liens d'onglets sont absolus (`/embarcations/tableau`) : un lien relatif se résout depuis l'adresse courante.
- Horaire (« Animation » dans l'app) : une semaine = un document (`horaire.horaires.etat`, mêmes clés que l'ancien créateur : cellules « gid|jour|période », fusions « gid|jour|indice »), édité via `useSemaine().modifier(fn)` (copie mutée puis enregistrement automatique après 600 ms). Réglages communs dans `horaire.parametres` (clé `reglages`). Animateurs = `core.employes` actifs. Toute la logique métier est dans `logique.ts` (fonctions pures, équivalence vérifiée avec l'ancien créateur). Dossiers : `horaire.dossiers` (un niveau, nom de semaine unique par dossier). Modèles de séjour : lignes de `horaire.horaires` avec `modele = true` (jamais dans un dossier) — toute liste de « semaines » doit les exclure. Jours, périodes et nuits d'un horaire : `restructurer` (le contenu suit son jour par nom et sa période) ; modèle posé sur d'autres jours : `decalerJours` (décalage par position). `etat.nuits` absent = nuits des réglages communs.
- Mastertimeline : `taches` est le modèle, valable d'une année à l'autre (`mois` = mois civils où la tâche revient, `intervalle_ans` + `exercice_depart` pour « aux N ans » ; `mois` null = ponctuelle, avec `echeance`). Chaque passage a sa ligne dans `coches` (`periode` = 'YYYY-MM' ou 'unique' ; statut 'faite' / 'sautee' = « pas cette année » ; `note` = note de l'année, la note de `taches` est permanente). Rien n'est recopié d'une année à l'autre. Exercice d'octobre à septembre, désigné par l'année où il commence (2026 = 2026-27). Toute la logique de dates est dans `calendrier.ts` (fonctions pures). Module en ligne seulement : mutations `networkMode: 'always'` (pas de file hors ligne) ; coches lues par exercice (`useCoches`), lectures paginées par 1000. Responsables = liste propre au module (pas `core.employes`). « Aux N ans » n'est pas modifiable dans la fiche (décision de la direction : une seule tâche s'en sert) ; la colonne `jour` n'est plus utilisée. `projets.entreprise_ids` = entreprises où le projet est offert dans la fiche (vide = toutes), voir `offertPour`.
- Cuisine (ex-Commande ; dossier `modules/commande`, schéma `commande`, module `commande`, adresse `/cuisine`) : un menu = une ligne de `commande.menus` (nom, jours, debut) ; ses groupes, grille, sorties et ajouts manuels sont dans leurs tables avec `menu_id` (lus par `useTableMenu(table, menuId)`, clé `[commande, table, menuId]` ; toute écriture porte `menu_id`). Recettes, consommables et banque restent communs (`useTable`). Dossiers : `commande.dossiers` ; modèles : `menus.modele = true` (ni dossier ni date). Copier un menu (dupliquer, modèle → menu) : fonction SQL `commande.copier_menu` (les groupes gardent leur id, clé `(menu_id, id)`) ; créer un menu vide : `commande.creer_menu` (menu + premier groupe en une transaction). Module en ligne seulement : mutations `networkMode: 'always'` ; une erreur affichée sur place est retirée du bandeau (`useOublierErreur`). Végé par groupe (`groupes_repas.vege`, comprises dans `portions`) : recette avec option végé → régulier = portions − végé ; en sortie, `sorties.groupes[].vege` = végé partis (au moins ceux qui ne tiennent plus au camp), servis par l'option végé de la glacière (`vegeSorties`). Diètes standard par groupe : `vege` (végétarienne, comptée dans la commande), `sans_porc`, `sans_lactose`, `sans_gluten` (information seulement) ; une diète par participant, régulière = portions − les autres. Participants avec allergies : `commande.participants` (clé étrangère `(menu_id, groupe_id)`, copiés par `copier_menu`) ; onglet « Groupes et diètes » (`Groupes.tsx`, une page imprimée par groupe), rappel par repas sur la feuille de cuisine. Impression : la feuille de cuisine a sa propre version papier compacte (`FeuilleImprimee`, un jour par page) ; l'horaire remplit une page paysage. Calcul de la commande dans `calcul.ts` (fonction pure ; avec végé = 0, identique à l'ancien calculateur, sauf qu'un même # produit en deux unités donne deux lignes : `cleLigne`) ; feuille de cuisine dans `cuisine.ts` (même calcul repas par repas : feuille + consommables = commande). Horaire du personnel : `personnel` (liste propre au module), `fonctions` (couleur), `quarts` (une case = texte libre par personne et par jour, heures lues par `quarts.ts`), réglages dans `parametres` (clé `horaire_cuisine`) ; copier ou vider une semaine : `commande.remplacer_quarts` (une transaction).
- Subventions (« Vigie de subventions », schéma et module `subventions`, adresse `/subventions`) : accès par la grille par rôle ou en ajout personnel (écriture ou rien ; admins seulement au départ). `subventions.a_acces()` = `core.peut_ecrire('subventions')` (RLS, déclenchement manuel du Worker par `peut_utiliser`) ; destinataires par défaut du courriel = profils actifs qui ont accès (`core.niveau_module_de`). Tables et colonnes en anglais, reprises telles quelles de la feuille de route (`grants`, `grant_companies`, `grant_feedback`…) ; fonctions SQL en français. Année fiscale du 1er octobre au 30 septembre nommée d'après l'année où elle **se termine** (`subventions.fiscal_year`, `anneeFiscale` dans `outils.ts` ; 2026 = « 2025-26 ») — l'inverse de Mastertimeline ; une subvention est rattachée à l'année de `granted_at`, sinon `received_at`, `deadline_date`, découverte (`dateRattachement`). Statuts : `nouveau` (pas regardée), `a_valider` (en attente d'une info), `rejete` (feedback obligatoire), `en_cours`, `obtenu`, `refuse` (refusée par l'organisme, ajout à la feuille de route), `expire`. Valider / rejeter passe par `subventions.decider` (statut + feedback en une transaction) ; un rejet n'est jamais reproposé. Dédoublonnage dans `subventions.inserer_resultats` : même adresse normalisée ou même `program_key` pour la même entreprise ; un programme obtenu/refusé/expiré une année précédente revient comme nouvelle édition (`previous_grant_id`). Notes et heures : modifiables seulement par leur auteur. Recherche : `worker/subventions/` (pipeline, prompts, appels Claude par le SDK officiel, courriel par l'API Gmail) ; le prompt (`invitationRecherche`) tire le contexte du groupe de `grant_companies` (rien à tenir à jour), met la priorité salariale seulement si `hires_staff`, et ajoute le réglage facultatif `consignes_groupe` (plus de « critères communs »), cron du lundi 8 h–11 h UTC partagé avec le waker (une entreprise par passage, journal `grant_search_runs`), routes `/api/subventions/{etat,recherche,courriel}` protégées par le jeton de session (`subventions.peut_utiliser`). Secrets Cloudflare seulement (README, section 8). Tests : `npm run test:worker` (réseau simulé). Erreurs affichées dans une fenêtre : racine de mutation `subventions-local` (le bandeau du module l'ignore).
- Styles : Tailwind v4, classes partagées dans `src/lib/ui.ts`, couleurs `foret-*` / `pierre-*` (`src/index.css`). Fond de page blanc. Cadre unique (`src/shell/Layout.tsx`) : pleine largeur et mêmes marges pour tous les modules — pas de largeur propre à un module (le menu et les marges ne doivent pas bouger d'un module à l'autre). Navigation : menu latéral à plat (pas de familles, décision du 2026-10-05), réductible aux icônes sur ordinateur (`lg`, choix retenu dans `localStorage`) ; sur téléphone, barre du haut + tiroir. `--largeur-menu` (0 de décalage hors `lg`) : un élément `fixed` centré en bas ajoute `lg:left-(--largeur-menu)` ; `--hauteur-entete` vaut 0 sur ordinateur (pas de barre du haut). Menus déroulants : flèche maison globale (`src/index.css`, règle hors couche qui impose l'espace à droite) ; `sans-fleche` pour un menu-bouton, `fleche-serree` pour un tout petit menu. Icônes : `src/lib/icones.tsx`. Saisie d'un nom : `SaisieNom` / `Bulle` (`src/lib/SaisieNom.tsx`) plutôt que `prompt()` ; confirmation : `await confirmer({ titre, message?, libelleOk?, danger? })` (`src/lib/Confirmation.tsx`, hôte `<Confirmations />` monté dans `main.tsx`) plutôt que `confirm()`.
- Node est dans `/usr/local/bin` (installateur officiel, pas Homebrew — macOS 14 non supporté par Homebrew).
- Vigie des camps (dossier `modules/vigie`, schéma `vigie`, adresse `/vigie`, accès par la grille par rôle ou en ajout personnel ; admins seulement au départ : RLS `core.peut_lire/peut_ecrire('vigie')`, fonction Edge par `core.niveau_module_de`) : rien de ce que Claude trouve n'est appliqué à un camp suivi sans validation — tout passe par `vigie.changements` (prix, nouveau programme, nouvelle activité), appliqué par `vigie.valider_changement` (une transaction). Exception : la passe 2 (`documentation`, lancée par le déclencheur quand un camp proposé devient inclus) remplit la fiche directement. Appels à Claude : une ligne par appel dans `vigie.requetes_ia` (file), envoyées en lot (Message Batches) par la fonction Edge `supabase/functions/vigie` (réveillée par pg_cron `vigie-tic` toutes les 10 min via `vigie.tic()`, seulement s'il y a du travail ; `vigie.planifier()` chaque jour lance la mensuelle le 1er et la découverte à `prochaine_decouverte`). `pause_turn` : la conversation est gardée dans `donnees.messages` et renvoyée au lot suivant. Activités = liste candidate commune (`activites`, pas de fiche par camp) liée par `camps_activites` ; une activité déjà offerte à la BPA (`offert_bpa`) est liée sans validation, seules les autres passent par `changements` ; un camp exclu reste en base pour ne jamais être reproposé. Catégories d'un camp : `leader` (leader de l'industrie, courte liste de la direction), `reference` (par défaut), `non_comparable` (pas un comparable, posé à la main : hors des métriques et de la vérification mensuelle) ; les métriques comptent les camps comparables (`estComparable` = inclus et pas `non_comparable`) et font ressortir les leaders. Prix par nuit = colonne générée. Maquette 3D : scène JSON de formes simples (boite, cylindre, sphere, cone ; mètres, y vers le haut), rendue sans bibliothèque en Canvas 2D (`Maquette3D.tsx`). Modèle par défaut : `claude-sonnet-5-5` (réglage `modele`). Pas de mémoire auto-apprenante : ajustements à la main dans Réglages (`consignes`). Import du Sheets : `scripts/migration/vigie.py`.
- Calendrier des opérations (dossier `modules/calendrier`, schéma et module `calendrier`, adresse `/calendrier`, direction + coordonnateurs cochés via `peut_lire`/`peut_ecrire`) : séjours = copie **en lecture seule** d'Airtable (base « Réservation Groupes », synchro à sens unique par le Worker : `worker/calendrier/synchro.js`, champs lus par identifiant `fld…`, cron aux 15 min partagé avec le waker — le tour de Subventions ne part qu'au passage de l'heure pile ; upsert + retrait logique en une transaction par `calendrier.synchroniser_sejours`, clé secrète seulement ; réservations « Closed lost » jamais affichées). **Rien n'est effacé** : pas de politique DELETE, « supprimer » pose `deleted_at` (`useRetirer`) ; `updated_by`/`updated_at` posés par le déclencheur `calendrier.auteur()` ; chaque changement va dans `calendrier.journal` (`journaliser()`, avec le nom de l'auteur). Cuisine : **pas de deuxième horaire** — la vue commune `v_presence_jour` (security_invoker, jamais d'heures) lit `commande.quarts` (OFF, Vacance… exclus par `quart_travaille`, mêmes règles que `travaille()` de Cuisine)  ; **animation : pas de deuxième horaire non plus** — elle vient du module Animation (Horaire) : un horaire daté (`horaire.horaires.debut`, date du premier jour, jamais pour un modèle ; un horaire sans date n'est pas dans le Calendrier) place chaque jour de `etat.jours` à la première date ≥ `debut` qui porte ce nom (`calendrier.date_du_jour` en SQL, `dateDuJour` dans `modules/calendrier/horaire.ts`) ; la vue prend l'animateur de chaque groupe (pendant son congé, le remplaçant, sinon personne ; identifiant = `core.employes` par surnom) ; pas d'onglet Animation (retiré à la demande de la direction : la rangée Animation de la grille suffit ; `/calendrier/animation` redirige) — le lien direct `/horaire?semaine=<id>` reste dans le module Animation ; direction et terrain = `presences_simples` (une ligne par personne, jour et secteur ; décocher pose `deleted_at`, recocher la réactive par upsert), saisies **directement dans la grille du Calendrier** (rangées Direction et Terrain, `CellulePresence` : fenêtre à cocher + note) — plus d'onglet Présences (`/calendrier/presences` redirige). Personnel = liste propre au module (direction et terrain ; secteur null = à préciser). Événements : récurrence RRULE simple lue par `recurrence.ts` (fonctions pures : DAILY, WEEKLY+BYDAY, MONTHLY par date ou par rang « 1MO », INTERVAL) ; `fin_recurrence` et `exceptions` en colonnes. Pas de vue du jour (retirée à la demande de la direction) : l'onglet Calendrier (`Vue.tsx`, adresse `/calendrier`) est l'accueil du module, en semaine, mois ou **période libre** (`?vue=periode&du=…&au=…`, au plus 62 jours ; un clic sur un séjour cadre la période sur son arrivée → départ) ; sous les séjours et les événements, une rangée par secteur : Direction et Terrain (modifiables), Cuisine et Animation (lues, avec un lien « modifier » vers leur module). Date affichée dans l'adresse (`?date=`, `useDateChoisie`), gardée d'un onglet à l'autre : l'historique = changer de date. Module en ligne seulement (`networkMode: 'always'`) ; erreurs affichées sur place : racine `calendrier-local`.
- Feuilles de temps (dossier `modules/temps`, schéma et module `temps`, adresse `/temps`) : **confidentiel**. Une personne de la direction ne voit que **sa** feuille ; un admin voit toutes les feuilles + l'onglet Tableau de bord ; coordonnateurs et tout rôle futur : jamais. Exception à la règle `core.peut_lire` : un seul endroit décide en base, la liste blanche `temps.role_autorise(role)` (`'admin','direction'`, à ne pas remplacer par `core.est_direction`) ; lecture par `temps.peut_voir(user_id)` (soi ou admin), écriture des heures et de la note par `temps.peut_modifier(user_id, jour)` (soi ou admin, en tout temps). Le module n'est ni dans `core.acces_modules` ni dans la grille `core.acces_roles` (`accesFixe` dans `modules.ts`) : ne jamais l'y ajouter. **Pas de temps réel** (les suppressions seraient diffusées sans filtre RLS) ni de cache sur l'appareil (requêtes `['temps', …]` exclues de la persistance dans `src/lib/requetes.ts`). Périodes de paie calculées, pas stockées : 14 jours du dimanche au samedi depuis le 4 octobre 2026 (`temps.debut_periode` en SQL, `periodes.ts` en TS, mêmes règles ; rien avant). `heures` : une ligne par personne, jour et type (`regulieres`, `vacances`, `maladie`), au quart d'heure, au plus 24 h par jour (déclencheur), 0 = ligne supprimée. **Pas de circuit d'approbation** (retiré à la demande de la direction le 2026-10-05 : ni soumission, ni approbation, ni verrouillage). `feuilles` : la note de la période, une ligne par personne et période, écrite seulement par `temps.enregistrer_note` (aucune politique d'écriture directe). Clés étrangères `on delete restrict` vers `core.profils` : registres de paie, on désactive un compte au lieu de le supprimer. Module en ligne seulement (`networkMode: 'always'`) ; erreur de note affichée sur place : racine `temps-local`.
- Véhicules (dossier `modules/vehicules`, schéma et module `vehicules`, adresse `/vehicules`, direction + coordonnateurs cochés via `peut_lire`/`peut_ecrire`) : une fiche par véhicule (`vehicules.vehicules`, surnom unique, type `minibus`/`voiture`/`vtt`/`remorque`/`autre`, affichés dans cet ordre, statut `en_circulation`/`remise` seulement), immatriculation et assurance = valeurs en cours + échéance sur la fiche (pas d'historique). Deux registres datés : `inspections` (la `prochaine` échéance de l'inspection **la plus récente** fait foi ; proposée à +6 mois : « au 6 mois si pas remisé », tâche Mastertimeline) et `entretiens` (`compteur` = km pour un minibus ou une voiture, heures pour un VTT, rien pour une remorque : `uniteCompteur`). Échéances calculées dans `outils.ts` (fonctions pures) : dépassée ou à 30 jours ou moins → encadré « À surveiller » ; un véhicule remisé n'est jamais signalé. Compagnies propriétaires = liste propre au module (`proprietaires`, `on delete restrict`). Photo : seau **public** `vehicules-photos` (chemin `<vehicule_id>/<uuid>.jpg` dans `vehicules.photo`), réduite à 1600 px en JPEG côté client avant l'envoi (`changerPhoto`), écriture réservée à `peut_ecrire('vehicules')` par les politiques de `storage.objects`. Supprimer un véhicule efface ses registres (cascade) et sa photo ; pour la saison morte, on le remise. Module en ligne seulement (`networkMode: 'always'`) ; erreurs des fenêtres affichées sur place : racine `vehicules-local`.
- Pokes (`core.pokes`, `src/shell/Poke.tsx` + `pokes.ts` ; pas un module : tous les profils actifs, hors grille d'accès ; **en DEV seulement**, pas en PROD tant que Maxime ne l'a pas approuvé) : **tout se passe dans le coin** (`CoinPoke` : pied du menu sur ordinateur, barre du haut sur téléphone ; choix de Maxime : rien au milieu de l'écran tant qu'on ne clique pas) : un petit 👉 discret ouvre la fenêtre d'envoi (personne + émoji) ; un poke reçu remplace le 👉 par un 🎁 ; un clic sur le cadeau fait exploser l'émoji partout (Web Animations, rien si `prefers-reduced-motion`) et ouvre un petit modal « X t'a poké ! » (Fermer seulement), rendu une seule fois par `FournisseurPoke` (monté par le Layout). Un envoi par personne et par jour (`unique (de, jour)`, `jour` = date de Montréal posée par la base), émoji parmi une liste fixe (contrainte de la table = `EMOJIS_POKE`). Envoi seulement par `core.poker` (aucune politique d'écriture ; poker quelqu'un en retour marque ses pokes vus), ouverture du cadeau = `core.marquer_pokes_vus` ; chacun ne lit que ses pokes envoyés/reçus ; liste des personnes par `core.collegues_poke()` (nom seulement, jamais le courriel). Pas de « Poker en retour », d'historique ni de notification push. Temps réel : un seul abonnement (`useTempsReelPokes`, dans `FournisseurPoke`). Rien n'est supprimé.
