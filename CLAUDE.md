# Gestion du camp — conventions

- Code, noms de tables, colonnes et variables **en français** (sauf les tables reprises telles quelles de l'ancien Commande : `name`, `cat`, etc.).
- Un schéma Postgres par module (`core`, `embarcations`, `commande`, `horaire`, `mastertimeline`, `subventions`, `vigie`, `calendrier`, `temps`, `vehicules`, `travaux`, `achats`, `rooming`, `caisse`, `ameliorations`, `reunions`, `crm`, `reservations` ; Coût par assiette est dans `commande`). Toute nouvelle table : RLS activée + politiques `core.peut_lire('<module>')` / `core.peut_ecrire('<module>')` (référentiel `core` : `core.est_direction()`).
- **Employés** (`core.employes`, Référentiel › Employés, premier onglet du référentiel) : `surnom` = « Nom de camp » à l'écran, `prenom` + `nom_famille` (demande de Maxime du 2026-10-07) ; `nom_complet` (« Nom, Prénom ») est posé par le déclencheur `core.poser_nom_complet`, ne jamais l'écrire ; plus de spécialités. Ordre des onglets du référentiel : Employés, Compagnies, Groupes, Semaines.
- **Compagnies** = `core.entreprises` (Référentiel › Compagnies, demande de Maxime du 2026-10-07 : une seule liste dans l'app ; nom, abréviation, description, couleur, ordre, active ; lue par toute personne active, modifiée par la direction). Ex-`mastertimeline.entreprises` déplacée telle quelle (mêmes id). S'en servent : Mastertimeline (tâches, `projets.entreprise_ids`), Achats, Véhicules (`vehicules.proprietaire_id`, ex-`vehicules.proprietaires`), Vigie de subventions (`grant_companies.entreprise_id`, une recherche par compagnie ; `grant_companies.name` = copie du nom tenue par la base : déclencheurs `subventions.nom_compagnie` et `core.renommer_compagnie`), Feuilles de temps (`core.employes.entreprise_ids`, heures par compagnie). Nouvelle liste de compagnies dans un module : non, utiliser celle-ci. Couleurs (Maxime, 2026-10-07) : GBPA+ vert, Opikawa orange, Aquabounga jaune, Rouge & Diable rouge, Trembloc brun, BPA inc. gris ; toute étiquette d'une compagnie = `PuceCompagnie` (`src/lib/PuceCompagnie.tsx`, teinte de sa couleur, `court` = abréviation), pastilles « choix » du référentiel teintées par `Option.couleur`.
- Qui voit quel module : **grille d'accès par rôle** `core.acces_roles` (rôle `direction`/`coordo`/`terrain` × module → `lecture`/`ecriture` ; absent = aucun), réglée par les admins dans la page Utilisateurs (décision du 2026-10-05). L'admin a tout, toujours. Un nouveau compte arrive avec le rôle `terrain` (défaut de `core.profils.role` depuis le 2026-10-06) : l'admin le change pour la direction ou un coordonnateur. Toute autre personne a en plus ses ajouts personnels (`core.acces_modules`, bouton « Ajouter un module » sur sa ligne) ; le niveau le plus élevé l'emporte. Seul endroit qui décide : `core.niveau_module_de(user, module)` (derrière `peut_lire`/`peut_ecrire`, la fonction Edge vigie, les destinataires de Subventions) ; même règle côté app dans `src/shell/acces.ts` (`niveauModule`, affichage seulement). Subventions et Vigie peuvent aussi aller aux coordonnateurs (décision du 2026-10-05) ; `sansLecture` : pas de mode lecture seule dans l'app (Subventions : écriture ou rien) ; `accesFixe` : hors grille (Feuilles de temps). Nouveau module : l'ajouter aux contraintes `module in (…)` de `acces_roles` et `acces_modules`, et à la grille de la direction si elle doit le voir.
- **DEV et PROD séparés** (depuis le 2026-10-06 : l'équipe utilise l'app). DEV = Supabase **local** dans Docker (`npm run db:start` / `db:reset` / `db:stop` ; Docker Desktop doit rouler, binaire dans `/Applications/Docker.app/Contents/Resources/bin`) ; `.env.local` vise la base locale (`http://127.0.0.1:54321`), **jamais la PROD**. Données de test : `supabase/seed.sql` (comptes `*@camp.test`, codes de connexion dans Mailpit, http://localhost:54324 ; `db:start` coupe le SMTP Gmail de `config.toml` par variable d'environnement). PROD = projet hébergé `nurjzafcogzgekquzuwh` : `npm run prod:db:push` (migrations) et `prod:db:config`, puis push sur `main` (Cloudflare publie). Une migration n'est appliquée en PROD qu'une fois testée en local et validée par Maxime.
- **Deux branches seulement** (décision de Maxime du 2026-10-06, il est seul à développer) : `dev` = la version DEV, où l'on travaille toujours (commit puis `git push` sur `dev` : simple sauvegarde, Cloudflare ne publie que `main`) ; `main` = la PROD, jamais modifiée directement. Un module à la fois : le finir et le mettre en ligne avant d'en commencer un autre. Mise en ligne uniquement par la commande `/mise-en-ligne` (fusion de `dev` dans `main`, migrations PROD, push), après un « oui » explicite de Maxime. Pas de branche de chantier ni de worktree. Nouvelle migration : nommée à l'heure **UTC** (`npx supabase migration new <nom>` ou `date -u +%Y%m%d%H%M%S`), jamais un numéro inventé.
- Les changements de base passent **toujours** par une migration dans `supabase/migrations/` (jamais d'édition manuelle dans le tableau de bord).
- Accès aux données côté client : `supabase.schema('<module>').from(...)` ; listes simples via `useListe` / `useEnregistrer` / `useSupprimer` (`src/lib/donnees.ts`), qui gèrent le temps réel.
- Seuls Embarcations et Travaux visent le mobile et le hors-ligne ; Cuisine et Horaire sont pensés pour ordinateur.
- Modifications hors ligne (voir `src/modules/embarcations/donnees.ts`) : chaque mutation a une clé fixe et est définie avec `clientRequetes.setMutationDefaults` (enregistrée dans `src/lib/requetes.ts` **avant** la restauration du cache), sinon une modification en attente ne peut pas reprendre après un rechargement. Mise à jour optimiste ligne par ligne ; le contexte ne garde que la ligne d'avant (jamais toute la liste). Identifiants créés côté client (`crypto.randomUUID()`).
- `gcTime` des requêtes : `Infinity` — jamais une durée > 24,8 jours (débordement de `setTimeout` : le cache restauré serait effacé aussitôt).
- Canaux temps réel : toujours un nom unique (`${nom}-${crypto.randomUUID()}`), sinon « cannot add postgres_changes callbacks after subscribe() » au remontage.
- Dans un module monté sur `<nom>/*`, les liens d'onglets sont absolus (`/embarcations/tableau`) : un lien relatif se résout depuis l'adresse courante.
- Horaire (« Animation » dans l'app) : une semaine = un document (`horaire.horaires.etat`, mêmes clés que l'ancien créateur : cellules « gid|jour|période », fusions « gid|jour|indice »), édité via `useSemaine().modifier(fn)` (copie mutée puis enregistrement automatique après 600 ms). Réglages communs dans `horaire.parametres` (clé `reglages`). Animateurs = `core.employes` actifs. Toute la logique métier est dans `logique.ts` (fonctions pures, équivalence vérifiée avec l'ancien créateur). Dossiers : `horaire.dossiers` (un niveau, nom de semaine unique par dossier). Modèles de séjour : lignes de `horaire.horaires` avec `modele = true` (jamais dans un dossier) — toute liste de « semaines » doit les exclure. Jours, périodes et nuits d'un horaire : `restructurer` (le contenu suit son jour par nom et sa période) ; modèle posé sur d'autres jours : `decalerJours` (décalage par position). `etat.nuits` absent = nuits des réglages communs.
- Mastertimeline : `taches` est le modèle, valable d'une année à l'autre (`mois` = mois civils où la tâche revient, jamais null : les tâches et projets ponctuels sont dans Travaux depuis le 2026-10-06 ; `intervalle_ans` + `exercice_depart` pour « aux N ans »). Chaque passage a sa ligne dans `coches` (`periode` = 'YYYY-MM' ; statut 'faite' / 'sautee' = « pas cette année » ; `note` = note de l'année, la note de `taches` est permanente). Rien n'est recopié d'une année à l'autre. Exercice d'octobre à septembre, désigné par l'année où il commence (2026 = 2026-27). Toute la logique de dates est dans `calendrier.ts` (fonctions pures). Module en ligne seulement : mutations `networkMode: 'always'` (pas de file hors ligne) ; coches lues par exercice (`useCoches`), lectures paginées par 1000. Responsables = liste propre au module (pas `core.employes`). « Aux N ans » n'est pas modifiable dans la fiche (décision de la direction : une seule tâche s'en sert) ; la colonne `jour` n'est plus utilisée. Entreprises = `core.entreprises` (référentiel, plus de liste propre depuis le 2026-10-07 ; l'onglet Réglages › Entreprises renvoie au référentiel). `projets.entreprise_ids` = entreprises où le projet est offert dans la fiche (vide = toutes), voir `offertPour`. Étiquettes (tags, demande de Maxime du 2026-10-06 : Corvée, ex-case à cocher, et Woofing) : liste du module `etiquettes` (Réglages), posées par `taches.etiquette_ids` (plusieurs par tâche) ; supprimer une étiquette la retire des tâches de Mastertimeline et de Travaux (déclencheur `retirer_etiquette`) ; filtre en puces (`ChoixEtiquettes`, `src/lib/Etiquettes.tsx` : plusieurs allumées = l'une ou l'autre) dans toutes les vues. Photos et PDF (demande de Maxime du 2026-10-07) : `fichiers`, joints à la **tâche** (le modèle, valables toutes les années, pas au passage), seau **privé** `mastertimeline-fichiers` lu par adresses signées (`useAdresseFichier`, requêtes `['mastertimeline-adresses', …]` jamais gardées sur l'appareil), même affichage que Travaux (`src/lib/PiecesJointes.tsx`) ; envoyés tout de suite depuis la fiche d'une tâche existante. **Un onglet par étiquette** (`VueEtiquette.tsx`, `/mastertimeline/etiquette/:id`, demande de Maxime du 2026-10-07, direction seulement : onglet de Mastertimeline) : tâches de Mastertimeline **et de Travaux** qui la portent, mois choisi + retards (Travaux : ouvertes = mois en cours, échéance passée = en retard ; autre mois = dues ou faites ce mois-là ; annualisées exclues).
- Cuisine (ex-Commande ; dossier `modules/commande`, schéma `commande`, module `commande`, adresse `/cuisine`) : un menu = une ligne de `commande.menus` (nom, jours, debut) ; ses groupes, grille, sorties et ajouts manuels sont dans leurs tables avec `menu_id` (lus par `useTableMenu(table, menuId)`, clé `[commande, table, menuId]` ; toute écriture porte `menu_id`). Recettes, consommables et banque restent communs (`useTable`). Dossiers : `commande.dossiers` ; modèles : `menus.modele = true` (ni dossier ni date). Copier un menu (dupliquer, modèle → menu) : fonction SQL `commande.copier_menu` (les groupes gardent leur id, clé `(menu_id, id)`) ; créer un menu vide : `commande.creer_menu` (menu + premier groupe en une transaction). Module en ligne seulement : mutations `networkMode: 'always'` ; une erreur affichée sur place est retirée du bandeau (`useOublierErreur`). Végé par groupe (`groupes_repas.vege`, comprises dans `portions`) : recette avec option végé → régulier = portions − végé ; en sortie, `sorties.groupes[].vege` = végé partis (au moins ceux qui ne tiennent plus au camp), servis par l'option végé de la glacière (`vegeSorties`). Diètes standard par groupe : `vege` (végétarienne, comptée dans la commande), `sans_porc`, `sans_lactose`, `sans_gluten` (information seulement) ; une diète par participant, régulière = portions − les autres. Participants avec allergies : `commande.participants` (clé étrangère `(menu_id, groupe_id)`, copiés par `copier_menu`) ; onglet « Groupes et diètes » (`Groupes.tsx`, une page imprimée par groupe), rappel par repas sur la feuille de cuisine. Impression : la feuille de cuisine a sa propre version papier compacte (`FeuilleImprimee`, un jour par page) ; l'horaire remplit une page paysage. Calcul de la commande dans `calcul.ts` (fonction pure ; avec végé = 0, identique à l'ancien calculateur, sauf qu'un même # produit en deux unités donne deux lignes : `cleLigne`) ; feuille de cuisine dans `cuisine.ts` (même calcul repas par repas : feuille + consommables = commande). Horaire du personnel : `personnel` (liste propre au module), `fonctions` (couleur), `quarts` (une case = texte libre par personne et par jour, heures lues par `quarts.ts`), réglages dans `parametres` (clé `horaire_cuisine`) ; copier ou vider une semaine : `commande.remplacer_quarts` (une transaction).
- Cuisine › **Coût par assiette** (dossier `modules/commande/couts`, tables `commande.couts_*`, adresse `/cuisine/couts`, demande de Maxime du 2026-10-07 ; remplace le Google Sheets « Suivi coût par assiette 2026 ») : **accès propre** dans la grille, module `cuisine_couts` (RLS `peut_lire/peut_ecrire('cuisine_couts')`) — c'est un espace de Cuisine, pas une entrée du menu : `parent: 'commande'` dans `modules.ts` (`estEntree` l'écarte du menu, de l'accueil et de `GRILLE_AVANT`) ; aucune ligne dans la grille (montre les salaires) : admins + Frédérique (responsable de la cuisine) en ajout personnel. Coût par assiette = (nourriture + salaires) ÷ assiettes. **Tout est rattaché à des jours** puis additionné selon **deux vues** (choix de Maxime du 2026-10-07) : **Année** = 12 mois civils d'octobre à septembre (calculés, rien à saisir) et **Camp d'été** = les semaines de `couts_semaines` (par année, définies dans l'onglet Semaines, sans chevauchement ; 8 proposées à partir du dernier dimanche de juin), avec l'écart de chaque semaine à la moyenne de l'été. Chaque vue a un graphique (`Graphique.tsx`, demande de Maxime du 2026-10-07) : trois petits graphiques en ligne sur le même axe (coût par assiette, coût, assiettes ; jamais deux échelles sur un même graphique), curseur et infobulle communs. Années (`couts_annees`) désignées par l'année où elles commencent (comme Mastertimeline). **Factures** (`couts_factures`, crédit = négatif) : comptées au `jour_impute` s'il est posé (date d'imputation à la main : nourriture livrée pour plus tard), sinon au jour de livraison. **Salaires** (`couts_salaires`) : un montant par période de paie (14 jours du dimanche, mêmes périodes que les Feuilles de temps) et par poste (`couts_postes`), partagé également entre les 14 jours (choix de Maxime : pas de pondération par l'horaire). **Assiettes** : menus datés de Cuisine calculés jour par jour (à chaque repas planifié — plat, salade ou dessert —, les portions des groupes présents ; un groupe en sortie compte), total corrigible par menu (`couts_menus`, réparti comme le calcul), plus groupes ajoutés (`couts_groupes`, personnes × repas répartis également du `debut` à la `fin` ; sans dates = à classer, pas compté ; l'année suit `debut`) ; `couts_annees.menus = false` : les menus ne comptent pas (2025-2026, importée du Sheets). Calculs dans `calcul.ts` (fonctions pures : `journalier` puis `tableau`). Pas de temps réel ni de cache sur l'appareil (`['cuisine-couts', …]` exclues de la persistance). Module en ligne seulement ; erreurs dans le bandeau de l'espace (racine `cuisine-couts`), fenêtres sur place (`cuisine-couts-local`). Import 2025-2026 dans la migration (10 semaines du Sheets ; factures placées par ✅ ailleurs que leur livraison = imputées au premier jour de la période du Sheets ; groupes datés sur leur période ; nourriture 142 645,61 $, assiettes 31 323, salaires 76 882,19 $ ; les totaux du Sheets ne comptaient que mai à septembre).
- Subventions (« Vigie de subventions », schéma et module `subventions`, adresse `/subventions`) : accès par la grille par rôle ou en ajout personnel (écriture ou rien ; admins seulement au départ). Entreprises de recherche (`grant_companies`) = profil de recherche d'une compagnie du référentiel (`entreprise_id` unique ; nom lu dans `core.entreprises`, ajout par un menu des compagnies sans recherche ; « Base de Plein Air Mont-Tremblant », l'OBNL = GBPA+). `subventions.a_acces()` = `core.peut_ecrire('subventions')` (RLS, déclenchement manuel du Worker par `peut_utiliser`) ; destinataires par défaut du courriel = profils actifs qui ont accès (`core.niveau_module_de`). Tables et colonnes en anglais, reprises telles quelles de la feuille de route (`grants`, `grant_companies`, `grant_feedback`…) ; fonctions SQL en français. Année fiscale du 1er octobre au 30 septembre nommée d'après l'année où elle **se termine** (`subventions.fiscal_year`, `anneeFiscale` dans `outils.ts` ; 2026 = « 2025-26 ») — l'inverse de Mastertimeline ; une subvention est rattachée à l'année de `granted_at`, sinon `received_at`, `deadline_date`, découverte (`dateRattachement`). Statuts : `nouveau` (pas regardée), `a_valider` (en attente d'une info), `rejete` (feedback obligatoire), `en_cours`, `obtenu`, `refuse` (refusée par l'organisme, ajout à la feuille de route), `expire`. Valider / rejeter passe par `subventions.decider` (statut + feedback en une transaction) ; un rejet n'est jamais reproposé. Dédoublonnage dans `subventions.inserer_resultats` : même adresse normalisée ou même `program_key` pour la même entreprise ; un programme obtenu/refusé/expiré une année précédente revient comme nouvelle édition (`previous_grant_id`). Notes et heures : modifiables seulement par leur auteur. Recherche : `worker/subventions/` (pipeline, prompts, appels Claude par le SDK officiel, courriel par l'API Gmail) ; le prompt (`invitationRecherche`) tire le contexte du groupe de `grant_companies` (rien à tenir à jour), met la priorité salariale seulement si `hires_staff`, et ajoute le réglage facultatif `consignes_groupe` (plus de « critères communs »), cron du lundi 8 h–11 h UTC partagé avec le waker (une entreprise par passage, journal `grant_search_runs`), routes `/api/subventions/{etat,recherche,courriel}` protégées par le jeton de session (`subventions.peut_utiliser`). Secrets Cloudflare seulement (README, section 8). Tests : `npm run test:worker` (réseau simulé). Erreurs affichées dans une fenêtre : racine de mutation `subventions-local` (le bandeau du module l'ignore).
- Boutons « Modifier » / « Supprimer » : toujours `BoutonModifier` / `BoutonSupprimer` (`src/lib/BoutonsAction.tsx` : même forme, crayon ; poubelle et texte rouge), avec un texte précis au besoin (« Supprimer la série »). Exception : les poubelles icône seule dans les listes compactes.
- Styles : Tailwind v4, classes partagées dans `src/lib/ui.ts`, couleurs `foret-*` / `pierre-*` (`src/index.css`). Fond de page blanc. Cadre unique (`src/shell/Layout.tsx`) : pleine largeur et mêmes marges pour tous les modules — pas de largeur propre à un module (le menu et les marges ne doivent pas bouger d'un module à l'autre). Navigation : menu latéral à plat (pas de familles, décision du 2026-10-05), réductible aux icônes sur ordinateur (`lg`, choix retenu dans `localStorage`) ; sur téléphone, barre du haut + tiroir. `--largeur-menu` (0 de décalage hors `lg`) : un élément `fixed` centré en bas ajoute `lg:left-(--largeur-menu)` ; `--hauteur-entete` vaut 0 sur ordinateur (pas de barre du haut). Menus déroulants : flèche maison globale (`src/index.css`, règle hors couche qui impose l'espace à droite) ; `sans-fleche` pour un menu-bouton, `fleche-serree` pour un tout petit menu. Icônes : `src/lib/icones.tsx`. Saisie d'un nom : `SaisieNom` / `Bulle` (`src/lib/SaisieNom.tsx`) plutôt que `prompt()` ; confirmation : `await confirmer({ titre, message?, libelleOk?, danger? })` (`src/lib/Confirmation.tsx`, hôte `<Confirmations />` monté dans `main.tsx`) plutôt que `confirm()`.
- Node est dans `/usr/local/bin` (installateur officiel, pas Homebrew — macOS 14 non supporté par Homebrew).
- Vigie des camps (dossier `modules/vigie`, schéma `vigie`, adresse `/vigie`, accès par la grille par rôle ou en ajout personnel ; admins seulement au départ : RLS `core.peut_lire/peut_ecrire('vigie')`, fonction Edge par `core.niveau_module_de`) : rien de ce que Claude trouve n'est appliqué à un camp suivi sans validation — tout passe par `vigie.changements` (prix, nouveau programme, nouvelle activité), appliqué par `vigie.valider_changement` (une transaction). Exception : la passe 2 (`documentation`, lancée par le déclencheur quand un camp proposé devient inclus) remplit la fiche directement. Appels à Claude : une ligne par appel dans `vigie.requetes_ia` (file), envoyées en lot (Message Batches) par la fonction Edge `supabase/functions/vigie` (réveillée par pg_cron `vigie-tic` toutes les 10 min via `vigie.tic()`, seulement s'il y a du travail ; `vigie.planifier()` chaque jour lance la mensuelle le 1er et la découverte à `prochaine_decouverte`). `pause_turn` : la conversation est gardée dans `donnees.messages` et renvoyée au lot suivant. Activités = liste candidate commune (`activites`, pas de fiche par camp) liée par `camps_activites` ; une activité déjà offerte à la BPA (`offert_bpa`) est liée sans validation, seules les autres passent par `changements` ; un camp exclu reste en base pour ne jamais être reproposé. Catégories d'un camp : `leader` (leader de l'industrie, courte liste de la direction), `reference` (par défaut), `non_comparable` (pas un comparable, posé à la main : hors des métriques et de la vérification mensuelle) ; les métriques comptent les camps comparables (`estComparable` = inclus et pas `non_comparable`) et font ressortir les leaders. Prix par nuit = colonne générée. Maquette 3D : scène JSON de formes simples (boite, cylindre, sphere, cone ; mètres, y vers le haut), rendue sans bibliothèque en Canvas 2D (`Maquette3D.tsx`). Modèle par défaut : `claude-sonnet-5-5` (réglage `modele`). Pas de mémoire auto-apprenante : ajustements à la main dans Réglages (`consignes`). Import du Sheets : `scripts/migration/vigie.py`.
- Calendrier des opérations (dossier `modules/calendrier`, schéma et module `calendrier`, adresse `/calendrier`, direction + coordonnateurs cochés via `peut_lire`/`peut_ecrire`) : séjours = copie **en lecture seule** d'Airtable (base « Réservation Groupes », synchro à sens unique par le Worker : `worker/calendrier/synchro.js`, champs lus par identifiant `fld…`, cron aux 15 min partagé avec le waker — le tour de Subventions ne part qu'au passage de l'heure pile ; upsert + retrait logique en une transaction par `calendrier.synchroniser_sejours`, clé secrète seulement ; réservations « Closed lost » jamais affichées). **Rien n'est effacé** : pas de politique DELETE, « supprimer » pose `deleted_at` (`useRetirer`) ; `updated_by`/`updated_at` posés par le déclencheur `calendrier.auteur()` ; chaque changement va dans `calendrier.journal` (`journaliser()`, avec le nom de l'auteur). Cuisine : **pas de deuxième horaire** — la vue commune `v_presence_jour` (security_invoker, jamais d'heures) lit `commande.quarts` (OFF, Vacance… exclus par `quart_travaille`, mêmes règles que `travaille()` de Cuisine)  ; **animation : pas de deuxième horaire non plus** — elle vient du module Animation (Horaire) : un horaire daté (`horaire.horaires.debut`, date du premier jour, jamais pour un modèle ; un horaire sans date n'est pas dans le Calendrier) place chaque jour de `etat.jours` à la première date ≥ `debut` qui porte ce nom (`calendrier.date_du_jour` en SQL, `dateDuJour` dans `modules/calendrier/horaire.ts`) ; la vue prend l'animateur de chaque groupe (pendant son congé, le remplaçant, sinon personne ; identifiant = `core.employes` par surnom) ; pas d'onglet Animation (retiré à la demande de la direction : la rangée Animation de la grille suffit ; `/calendrier/animation` redirige) — le lien direct `/horaire?semaine=<id>` reste dans le module Animation ; direction et terrain = `presences_simples` (une ligne par personne, jour et secteur ; décocher pose `deleted_at`, recocher la réactive par upsert), saisies **directement dans la grille du Calendrier** (rangées Direction et Terrain, `CellulePresence` : fenêtre à cocher + note) — plus d'onglet Présences (`/calendrier/presences` redirige).
